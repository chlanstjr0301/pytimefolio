% 1. INTRODUCTION

\seclabel
\claim{1\quad Without a published API, we measured the server through the requests its web client makes}

\lead{We are building an API wrapper so that a program, rather than a person at a browser, can trade in the contest.} Road to Fund Manager is a paper-trading contest run by Timefolio Asset Management; participants enter tickers and target weights on a web page. An algorithmic strategy needs to log in, read balances, follow positions as they change and place orders on its own. The wrapper handles that communication so the strategy code never deals with tokens, sockets or date formats.

\lead{The organiser publishes no API, so every assumption the wrapper makes has to come from observation.} That covers how authentication works, how long tokens last, how dates are read and what the live messages contain. Guessing is risky because the server rarely complains: as Section~2.3 shows, a wrong date returns another day's data with HTTP 200, so a wrong assumption produces wrong numbers instead of an error.

\lead{The organiser allows automated orders within two limits.} In reply to our enquiry on 24 Nov 2026, the organiser stated that it provides no official API and does not prohibit automating orders with scripts or web drivers. An account that places 100 or more orders in a day may have its IP address blocked, and so may traffic that loads the system in a short time; the organiser recommends a delay between requests. We kept a copy of the reply. We ran no load or rate-limit tests; our busiest test sent about five requests per second for one second (Section~2.1).

\lead{We worked in three steps.} First we observed: after logging in we extracted API paths and live-feed method names from the JavaScript the site serves, and recorded WebSocket messages in the browser's developer tools. Then we reproduced each request with curl to read headers, cookies and response bodies; for the WebSocket, which curl cannot handle, we implemented the SignalR protocol in Python without a client library. Where a behaviour had more than one explanation, such as the condition for a delta, we wrote down the competing hypotheses and designed requests that would give a different result under each.

\lead{The report runs from measurement to design to orders.} Section~2 covers the protocol layers: transport (2.1), authentication (2.2), queries (2.3) and the live feed (2.4); most of it was measured before the open and rechecked after 09:00 where the session could change the result. Section~3 sets out the wrapper's goals, constraints and structure. Section~4 covers the order layer, tested during the session. Section~5 tests the finished wrapper against the live server: its start-up, feed and orders (5.1), the check that keeps orders from rounding to zero shares (5.2) and the contest's investment guidelines (5.3). \figref{2} gives the test setup; Appendix~A defines the terms and Appendix~B lists the design decisions with their evidence.

% 2.1 TRANSPORT
% =====================================================================================================
\seclabel
\claim{2.1\quad Reusing one HTTP/2 connection cuts a request from 106.5\ms{} to 16.0\ms}

\lead{The site runs on HTTP/2 over TLS 1.3 and does not offer HTTP/3.} The TLS handshake selects HTTP/2 through ALPN, and responses carry no \code{alt-svc} header, so the server does not advertise HTTP/3 (QUIC). The handshake uses TLS 1.3 with \code{TLS_AES_256_GCM_SHA384} and a four-certificate chain from Let's Encrypt.

\lead{The two channels share the upper layers and differ below them (\figref{3}).} A REST request travels as one HTTP/2 stream carrying the \code{Authorization: Bearer} header; later requests open new streams on the same connection and skip DNS, TCP and TLS altogether. An nginx front end receives the request (its own HTML error page appears when a request body is malformed, Section~2.2) and passes it to the ASP.NET application, which its error messages and its SignalR hub identify. The live feed starts with an ordinary HTTP/2 POST to negotiate, then opens a second connection and upgrades it with an HTTP/1.1 \code{Upgrade: websocket} request. The second connection is the server's doing, not our client's: the server's HTTP/2 settings frame does not include \code{ENABLE_CONNECT_PROTOCOL}, so it does not support WebSockets over HTTP/2 (RFC 8441), and any client, a browser included, needs a separate connection.

\Needspace{70mm}\figblock[wide]{3}{REST requests share one HTTP/2 connection; the live feed needs a second connection, upgraded to a WebSocket}[Layers per channel, from the server down to the connection set-up]{%
\input{figs/fig03.tex}}{The server's SETTINGS frame was read with Python's \code{h2} library. The front end is identified by its error page, the application by its error messages.}{DART Quant Team}

\lead{Most of the cost of a new connection is set-up, and a reused connection avoids it.} We sent five requests to the same endpoint (\code{Portfolio/Violations}) in one curl run and repeated the run ten times at one-second intervals. The first request in each run pays for the DNS lookup, the TCP connection and the TLS handshake; the other four reuse the connection (\figref{4}). The stage medians add up to 106.0\ms; the median of the totals, 106.5\ms, comes from different runs.

\figblock[wide]{4}{A new connection costs 106.5\ms, a reused one 16.0\ms; DNS varies the most}[Time per stage of a REST request, 10 runs (40 reused requests); bars are medians, dots single runs]{%
\input{figs/fig04.tex}}{curl's \code{time_*} values are cumulative from the start of the request; stage times are differences between adjacent values. ``Request to first byte'' runs from the end of the TLS handshake to the first byte of the reply. All 50 requests returned HTTP 200. 06:03 KST, 24 Nov 2026.}{DART Quant Team}

\lead{Two of the stages are specific to our set-up, not to the server.} WSL keeps no DNS cache, so every new connection paid 30 to 94\ms{} for a lookup that a desktop system would usually answer from its cache. curl's 28.9\ms{} for TLS also includes its own start-up: timed in Python on an open TCP connection, the TLS 1.3 handshake itself took 12.4\ms, one round trip. The TCP stage varies by only 0.9\ms, so the network path is stable. Taking the 11.1\ms{} round trip out of the 16.0\ms{} reused request leaves about 5\ms{} on the server, so a wrapper request is almost all network latency.

\lead{The server closes an idle connection after 15 to 30\,s.} httpx itself drops a connection after 5\,s idle by default, which hid the server's behaviour in our first try. With that limit raised to 600\,s, a connection was reused after 5\,s and 15\,s of silence and replaced after 30\,s. A wrapper that keeps the connection longer than the server does will send its next request into a closed socket and pay for a retry, so the wrapper's own limit has to sit below 15\,s.

\lead{From the Python client during the session, a request on a reused connection took 31 to 39\ms.} That is about twice curl's 16.0\ms{} before the open; the two figures differ in client, time of day and market-hours load, and we have not separated these causes. The first request of a fresh process took 1.2 to 1.3\,s, almost all of it one-time module loading and SSL set-up (the virtual environment lies on the Windows drive). A second client created in the same process paid 130\ms{} for its new connection, so the one-time cost belongs to the process, not to the connection.

\lead{We discarded an earlier run of the timing test because it mixed in failed requests.} It used a token that had already expired, and we had not recorded status codes; its fastest reused requests, 12.2\ms, fit a server rejecting the token before touching any data. \figref{4} uses only the repeat run, with a valid token and a status code on every request.
\verdict{the wrapper keeps one \code{httpx.AsyncClient(http2=True)} for the life of the process, with \code{keepalive_expiry} set to 10\,s, below the server's 15\,s. It connects by host name, since the certificate names \code{contest.timefolio.net}; connecting by IP address would save one lookup at the cost of hostname verification. At start the wrapper calls \code{warm_up()}, which sends one cheap request, so the 1.2 to 1.3\,s start-up cost is paid before the first order.}

\seclabel
\claim{2.2\quad A 900-second token and seven-day cookies that renewal never extends and logging out never revokes}

\lead{Logging in returns the access token and the list of portfolios in one reply.} \code{POST /api/Auth/Login} with \texttt{\{"email", "password"\}} returns HTTP 200, a 435-character JWT access token (\code{accessToken}), six portfolios (\code{pfs}), 16 contests (\code{ctsts}) and the server's current business day (\code{currBizDay}). The same reply carries the participant's phone number and date of birth, so the wrapper keeps only the fields it needs and never logs this reply in full.

\lead{The login reply sets five credentials with different lifetimes; the wrapper manages the first two (\figref{5}).}

\lead{Renewal needs the cookies set at login, and it does not move the seven-day deadline.} \code{POST /api/Auth/SilentRefresh} with the root-path cookies and no \code{Authorization} header returns HTTP 200 and a new access token. Sending \code{refreshToken} alone was refused with a 401, so the wrapper keeps and sends the whole cookie jar. The refresh cookie's expiry was 20:38:54 UTC on 30 Nov both before and after the call, and the reply set no new \code{refreshToken}. Renewal therefore neither slides the expiry forward nor rotates the token, and repeated renewals with the same cookie all succeeded. During the session two \code{SilentRefresh} calls sent at the same moment with the same cookies both returned 200, a third sent right after also returned 200, and none set a new \code{refreshToken}; concurrent renewals do not invalidate each other.

\lead{The server accepts an expired access token for 300\,s.} A first test bracketed the cut-off between 3.5 and 5.6 minutes after expiry. A second token, issued at 08:16:43 by the server's clock, was sent again just before and after five minutes past its expiry: by the server's \code{Date} header it was accepted 4~min~57\,s after expiry and refused 5~min~07\,s after (\figref{6}). The cut-off lies inside that 10-second interval, which matches the 300-second default clock skew in ASP.NET's JWT validation; the 401's wording also comes from Microsoft's .NET identity library.

\figblock[wide]{6}{The server accepts a token up to 300\,s after expiry; the refresh cookie's deadline stays fixed through renewal}[Lifetime of one access token and of the refresh cookie from the 05:38:54 login; tolerance edges from the second test, placed relative to expiry]{%
\input{figs/fig06.tex}}{Times are KST. The 401 carried \code{www-authenticate: Bearer error="invalid_token", error_description="The token expired at ..."} (UTC). Token lifetime read from the decoded JWT; cookie expiry from \code{Set-Cookie} before and after renewal.}{DART Quant Team}

\lead{Our PC clock ran 3\,s ahead of the server's, and that matters for timing expiry.} In the second test the local clock read 08:36:43 when the server's \code{Date} header read 23:36:40 UTC. A wrapper that schedules renewal by its own clock against the JWT's \code{exp} inherits that error, so it measures the offset from the \code{Date} header of each reply and corrects for it.

\lead{A malformed request and a failed login get different errors from different parts of the stack.} A request body with broken JSON (a raw carriage return inside a string) drew an HTML 400 page in nginx's format. Valid JSON with wrong credentials drew a 401 from the API. A 400 points to a bug in the code that built the request and will fail again on retry; a 401 is cured by a token refresh or a new login.

\lead{Logging in again leaves the existing session working.} After a second login on the same account, the first session's cookies still renewed its token, and the browser stayed logged in after a page reload. The wrapper and the web page can therefore run at the same time.

\lead{Logging out asks the browser to delete its cookies and revokes nothing on the server.} \code{POST /api/Auth/Logout} returned 200 with the body \texttt{\{\}} and \code{Set-Cookie} headers that blank \code{refreshToken}, \code{userid} and \code{asset_token} with an expiry date in 1970. We had saved a copy of the refresh cookies before the call. After the logout that copy still renewed the token (\code{SilentRefresh} 200), the access token issued before the logout still worked on REST (200), and two other sessions of the same account kept working. Anyone holding a copy of the cookie jar can therefore obtain access tokens until the seven-day expiry, whatever the owner does in the browser. Each login also adds one more session that lives seven days.
\verdict{the wrapper renews the access token through \code{SilentRefresh} 12 minutes after issue by the server's clock, or at once on a 401, after which it repeats the request once; a 401 is sent before the server acts on the request, so repeating even an order cannot create a duplicate. It never logs in while the stored session works, since every login adds a session that cannot be ended early. It logs in with the stored credentials only when renewal fails or when the cookie jar has less than one day left, so the seven-day expiry never falls in the middle of a session. The cookie jar is a credential that logging out cannot revoke, so the wrapper stores it outside the repository with owner-only permissions (mode 0600), and it does not call \code{Logout} on shutdown, since the call ends nothing on the server and would blank the stored jar, which forces a new login, and a new session, at the next start. A 400 is raised as an error without retrying. The 300\,s tolerance is a server setting that can change, so the schedule does not rely on it.}

The Sunday reply differs from the 23 Nov reply in one value, the weight of the portfolio's only small-cap stock. Its price did not change on 23 Nov (previous close and close both KRW~14,840), while the portfolio's value fell 3.59\% that day. A stock whose price stays flat gains weight as the portfolio shrinks, so its 20 Nov weight should be $3.33 \times (1 - 0.0359) = 3.21$, the value the Sunday request returned.

\claim{2.4\quad The live feed answers only when asked, and sends a delta only for an exact echo of the previous t}

\lead{Connecting to the SignalR hub takes four steps (\figref{11}).} Balances, orders and sector weights come through an ASP.NET Core SignalR hub at \code{/hubs/main}. Navy arrows are sent by the client, grey arrows by the server.

\Needspace{100mm}\figblock[wide]{11}{After an HTTP negotiation, a WebSocket connection and a handshake, the client asks and the server answers}[Connection steps and message format; every message is one JSON object followed by the separator byte 0x1E]{%
\input{figs/fig11.tex}}{In a browser recording from 28 Oct 2026 the client sent each request 3\,s after the previous reply. Type 1 is an invocation of a method on the other side; type 6 is a ping and type 7 a close.}{Browser developer tools, Python implementation, DART Quant Team}

\lead{The hub sends nothing unless asked, before or during the session.} In the browser recording the browser asks again 3\,s after each reply. Our client got the same behaviour before dawn with \code{auto} set to true and to false, with replies in 20 to 84\ms. From 09:05 to 09:08, with prices moving, a client that sent one request and then stayed silent for 60\,s received nothing but the type-6 pings every 15\,s. The wrapper therefore has to send every request itself.

\lead{On the same connection, echoing the previous reply's \code{t} returns only what changed.} A request with \code{lastT=0} returns a snapshot of 9,915 bytes holding balances (\code{bs}), orders (\code{ords}), positions (\code{pos}) and market sector weights (\code{msecs}), plus five smaller top-level fields that Section~5.3 uses for the contest's guidelines. A request carrying the previous reply's \code{t} as \code{lastT} returns an empty delta of 577 bytes in which those four fields are \code{null} and \code{pos_diff}, \code{ords_diff} and \code{msecs_diff} appear instead, each with the fields \code{added}, \code{removed}, \code{updated} and \code{ords_chgd}. One more case: right after our order (Section~4) one reply had \code{null} arguments, so the receive loop must accept an empty reply and fall back to a snapshot.

\lead{During the session a delta is about one eighth of a snapshot.} At 3\,s polling the snapshot grew to 11,344 bytes (9,915 before the open) and deltas ran from 1,053 to 1,912 bytes, about 1.4\,kB on average, against one seventeenth of a snapshot for the empty deltas before the open. \code{pos_diff.updated} listed 8 to 23 of the 23 holdings per reply, and \code{msecs_diff} changed about every fourth reply (about 12\,s). \code{t} advanced by 3 per reply and sometimes by 4, so it follows wall-clock seconds.

\lead{\code{updated} carries only the changed fields of each record, keyed by the record's \code{Id} as a string.} Two entries from one reply read \code{"5745534": {"close": 89900, "prft": 1008000}} and \code{"5745535": {"close": 1180000, "prft": 3230000, "chPct": 8.76, "wei": 4.86}}: 2 to 4 of the 28 keys a position record has in a snapshot (Appendix~A lists all 28). \code{ords_diff} has the same form, for example \code{{"added": [], "removed": [], "updated": {"1649882": {"cumQty": 6, "avgPx": 352416.67}}, "ords_chgd": {}}}. Snapshot records carry \code{Id} as an integer, so a delta key used as it arrives would match no record; the wrapper converts each key with \code{int()} before merging. The keys are position record IDs, not tickers (\code{prodId}), so the wrapper also keeps an index from \code{prodId} to \code{Id}.

\lead{Merging deltas this way reproduces the server's state exactly, so goal G2 is met.} At 09:35 two connections polled the hub at the same moments for 15 rounds. Connection A applied deltas, merging the \code{updated} fields by \code{int(Id)}; connection B asked for a full snapshot every round (\code{lastT=0}). In all 15 rounds both connections received the same \code{t}, and A's accumulated \code{pos} and \code{ords} records equalled B's snapshot field for field: 0 differences in 15 of 15 rounds. An earlier check compared the merged state with a snapshot taken about 3\,s after the last delta and found 13 records that differed only in \code{close}, \code{prft}, \code{wei} and \code{chPct}, the fields that move with prices in 3\,s; comparing replies with the same \code{t} removes that gap.

\lead{We tested three rules for when the server sends a delta.} (a) \code{lastT} matches the \code{t} last sent on this connection; (b) \code{lastT} is any recent time; (c) \code{lastT} matches the \code{t} last sent to this account, on any connection. We varied \code{lastT} over eleven requests on two connections so that the rules predicted different replies (\figref{12}).

\figblock[wide]{12}{Only rule (a) predicts every reply; (b) fails at five steps and (c) at one}[Predicted and observed reply type by \code{lastT} sent; eleven requests 3\,s apart on two connections, 06:06 KST, 24 Nov 2026]{%
\input{figs/fig12.tex}}{Shaded cells with $\times$ are predictions the observation contradicts; grey text marks predictions it confirms; in the Observed column, deltas are shaded; ? marks a step where the rule predicts nothing definite. \lead{Rule (a) is the only one consistent with all eleven replies.} The server appears to keep, for each connection, the last snapshot it sent and its \code{t}. When \code{lastT} equals that \code{t}, it sends the current state minus that snapshot; otherwise it sends everything. Either way, the current state becomes the new reference.

This rule keeps the wrapper's state in step with the server. If a reply is lost, the next request carries an old \code{t}, the server sees no match and sends a snapshot, so the client can never apply one delta after skipping another. A reconnect also gets a snapshot without special handling. Sending a second request before the first reply arrives does no harm to correctness, but the second \code{lastT} is already stale, so the reply is a full snapshot, 17 times the size of an empty delta before the open.

\lead{\code{t} runs exactly nine hours (32,400\,s) ahead of Unix time.} A reply received at 05:48:27 KST carried \code{t} = 1795499307. Read as UTC that is 05:48:27 on 24 Nov, matching the reply's \code{kstNow}, but the Unix time of 05:48:27 KST is 1795466907. The server evidently converts Korean wall-clock time to epoch seconds as if it were UTC. Other timestamps are correct: the JWT \code{exp} is true Unix time and order records carry UTC strings ending in \code{Z}. Under rule (a) the offset does no harm as long as the client echoes \code{t} without computing with it.

\lead{An open WebSocket keeps working after its token expires, but a new connection needs a valid token.} We opened a connection with a token expiring at 07:21:41 and kept polling every 3\,s (\figref{13}). Replies kept arriving for 8 minutes past expiry, 382 in all, past the 300\,s after which REST requests are refused. A negotiation sent afterwards with the same token got a 401. The server therefore checks the token when a connection is made, not on each message, which matches the default in ASP.NET Core SignalR.

\lead{The first version of \code{guidelines()} put IT over its limit, and the server's count exposed the error.} It keyed the market sector weights by the \code{msecs} record \code{Id} instead of the sector code \code{sec}. \lead{\code{plan()} checks every target set against the contest rules before it creates any order.} In order, it raises \code{ValueError} when the targets sum above \code{max_total} (100\%), caps each held stock at its \code{weiLimit}, raises when a target names a stock outside the universe, and raises when a sector's total exceeds max(2 $\times$ market weight, 10\%), the check of \code{sector_violations()} in \code{orders} (D23). The sector of each stock comes from \code{Universe}, which the client loads once at start (2,648 stocks); the market weights come from \code{msecs} at each call. The server blocks a stock order outright but reports sector breaches only as counts after the weights have moved, so the wrapper checks sectors itself. It rejects instead of spreading the excess, as water-filling does for a stock: spreading a sector's excess would lower every stock in that sector and raise all the others, and each changed stock costs one of the 80 daily orders. The error names the sector, its total and its limit, so the caller can adjust.
